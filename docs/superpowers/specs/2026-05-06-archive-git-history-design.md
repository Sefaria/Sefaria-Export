# SC-43976 — Move Sefaria-Export Git History to a Separate Archive Repo

**Status:** Design
**Story:** [sc-43976](https://app.shortcut.com/sefaria/story/43976)
**Type:** chore
**Author:** yodem (Claude assisted)
**Date:** 2026-05-06

## Problem

`Sefaria-Export` is ~10 GB to clone because the git history accumulates monthly snapshots
of `books.json` (a 20 MB index regenerated by CI every month). The repo's *current* working
tree is small (~22 MB); the history is the cost.

Users who only want the export tooling (the `examples/` scripts, the `books.json` index, the
README) end up cloning gigabytes of historical `books.json` blobs they will never read.

## Goal

A clone of `Sefaria-Export` should be small (≤ ~50 MB) by default, while preserving the full
historical record in a discoverable, immutable archive repo.

Non-goals:
- Removing data from the GCS bucket. Bucket contents are unaffected.
- Changing the monthly regeneration of `books.json`.
- Rewriting any other Sefaria repository.

## Approach

Two-repo split:

1. **`Sefaria/Sefaria-Export-Archive`** — new repo. Mirror clone of the current full
   history at the moment of the freeze. Read-only afterwards (archived in GitHub settings).
2. **`Sefaria/Sefaria-Export`** — existing repo. Replaced with a single orphan commit
   containing the current working tree. Force-pushed.

### Why this approach (vs. alternatives)

| Option | Pros | Cons |
|--------|------|------|
| **Two-repo split (chosen)** | Matches story proposal. Clean. New clones are tiny. History remains accessible. | Force-push rewrites all hashes; breaks open PRs and forks. |
| `git filter-repo` to drop large blobs in place | Preserves commit graph & hashes for non-`books.json` paths | Still rewrites all hashes from first `books.json` commit forward. Same disruption, less clean separation. Doesn't actually solve "separate archive repo" goal. |
| Switch users to `--depth 1` and do nothing to the remote | Zero risk | Doesn't fix the size problem for anyone who clones normally; the GitHub web UI and `git clone` defaults still pull 10 GB. |

We accept the force-push cost once, in exchange for a permanently lean repo.

## Migration Plan

Executed by a **maintainer with admin rights on the Sefaria GitHub org**, not by automation
in this repo. The scripts in `scripts/migration/` are runbooks, not CI.

### Phase 0 — Preconditions
- All open PRs against `Sefaria-Export` are merged or closed (or PR authors are notified
  they will need to rebase onto a new root).
- `master` is green (latest `generate-books-json` workflow run succeeded).
- Maintainer has push access to both repos and a clean local checkout.

### Phase 1 — Create the archive repo
1. Create empty repo `Sefaria/Sefaria-Export-Archive` on GitHub (public, no README).
2. Run `scripts/migration/01_create_archive.sh`:
   - `git clone --mirror https://github.com/Sefaria/Sefaria-Export.git`
   - `git remote set-url --push origin git@github.com:Sefaria/Sefaria-Export-Archive.git`
   - `git push --mirror`
3. Verify: archive repo shows the full commit graph and the same `master` HEAD.
4. In GitHub settings for `Sefaria-Export-Archive`: enable "Archive this repository"
   (read-only). Add a clear `README.md` via the GitHub web editor pointing back to
   `Sefaria-Export`.

### Phase 2 — Slim the main repo
1. From a fresh clone of `Sefaria-Export`:
2. Run `scripts/migration/02_orphan_master.sh`:
   - Capture the current `master` SHA as `PRE_MIGRATION_SHA` for the announcement.
   - `git checkout --orphan fresh-master`
   - `git add -A && git commit -m "Reset history; full archive at Sefaria/Sefaria-Export-Archive (was <PRE_MIGRATION_SHA>)"`
   - `git branch -M fresh-master master`
3. Tag the pre-migration tip in the **archive** repo as `pre-migration-master` for easy
   reference.
4. Force-push `master` to `Sefaria-Export`:
   - `git push --force-with-lease origin master`
5. In GitHub settings for `Sefaria-Export`: temporarily disable branch protection on
   `master` for the force-push, then re-enable it.

### Phase 3 — Update the live repo
On the new lean `master`, in a regular PR:
- Update `README.md` to add a "Cloning" section pointing to `--depth 1` and the archive.
- Update `CLAUDE.md` similarly.
- Move the runbook scripts to `scripts/migration/` (if not already merged pre-migration).
- Add `docs/HISTORY.md` linking to the archive repo.

### Phase 4 — Announce
- GitHub release on `Sefaria-Export` titled "Repository slimmed; history moved to
  Sefaria-Export-Archive".
- Pinned issue with migration FAQ:
  - "Where did my old commit hashes go?" → archive repo.
  - "I had a fork / open PR." → re-fork or rebase onto the new root commit.
  - "I had a submodule pinned to an old SHA." → point submodule at the archive repo.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Open PRs become un-rebasable | Phase 0 gate. Communicate 1 week in advance. |
| Forks become disconnected | Document explicitly. Most consumers use the bucket, not forks. |
| Submodule pins / external scripts referencing old SHAs | Old SHAs all live in the archive — pins still resolve there. Document the redirect. |
| Force-push fails due to branch protection | Phase 2 step 5: temporarily relax protection. |
| Archive accidentally written to | Phase 1 step 4: enable GitHub "archive" mode. |
| Maintainer mis-runs the script | Scripts are `set -euo pipefail`, print plan, prompt before destructive steps, use `--force-with-lease`. |

## Verification

After Phase 2:
- `git clone https://github.com/Sefaria/Sefaria-Export.git /tmp/check && du -sh /tmp/check/.git`
  — expect well under 100 MB.
- `git -C /tmp/check log --oneline | wc -l` — expect 1.
- The monthly `generate-books-json` workflow runs successfully on the next scheduled trigger.
- `Sefaria-Export-Archive` clone reproduces the pre-migration HEAD SHA byte-for-byte.

## Deliverables in *this* PR (sc-43976)

This PR does **not** perform the migration. It lands the design and the runbook so the
maintainer-executed migration is fully scripted and reviewed before it runs.

1. `docs/superpowers/specs/2026-05-06-archive-git-history-design.md` — this document.
2. `scripts/migration/01_create_archive.sh` — Phase 1.
3. `scripts/migration/02_orphan_master.sh` — Phase 2.
4. `scripts/migration/README.md` — runbook overview, ordering, prerequisites.
5. `README.md` — add a "Cloning" section now (it's already best practice to suggest
   `--depth 1`, regardless of when the archive repo lands).

The actual force-push is a separate, manual maintainer action. The design will be reviewed
on this PR before that action is scheduled.
